### Product decisions

The owner settled these. A step may cite one as `product decision N`.

1. Scope is one pass. Every item below lands in this plan.
2. Stability covers: the terminal defects; `/login` for API-key providers; the load-sensitive tests; drift between the documents and the code; the absent Codex methods (`review/start`, `mcpServerStatus/list`, `config/batchWrite`, `command/exec`, `fs/*`); and pinned writes on Windows.
3. The terminal gets: tool rows, diffs, streaming Markdown, reasoning collapse, plan and subagent progress, a status band, a working indicator, four themes with fallbacks and `NO_COLOR`, notifications, welcome and exit rows, a window title, multi-line editing, history, a slash palette, `@file` completion, paste chips, `!` shell mode, image paste, an approval card, pickers, a visible follow-up queue, an Esc interrupt guard, a help panel, mouse wheel scrolling in lists and in the review, and a rewind gesture. It gets no key for an external editor.
4. The screen model is an inline dock and a full-screen review that opens only by key. The transcript stays in the terminal's own scrollback. The section "Terminal screen design" gives the rules: a finished row is written once; the dock keeps its height; a value that changes with time keeps its place; the client never clears the screen.
5. The dock holds, from the top: the composer, an open panel, the live row, and the status band. The live row is always there. A hint replaces text in the live row. `?` on an empty composer opens the key list.
6. The setting `verbosity` has the values `low`, `medium` and `high`, and its default is `medium`. While a block streams, the live row shows its tail on one row. `high` writes every block in full. `medium` writes thinking and code-mode code as one row, keeps diffs, and keeps the last 10 lines of command output. `low` writes one summary row for each group of tool calls. A failed item always keeps its last lines. `ctrl+o` opens the full text in the review at every level.
7. `/settings`, `/login`, `/model`, the model presets and every other slash command are interactive: each opens a panel with keyboard navigation, checks its input on submit, and has no dead end.
8. The ask tool uses the Codex wire request `item/tool/requestUserInput`. It is a read-class tool in `internal/tool/ask`. The answer is the tool output, and no journal event is added. One call carries 1 to 4 questions. Each question has 2 to 6 options with a label and a description, an optional preview, optional multi-select, and an automatic "Other" row. The recommended option is first. A cancel and a timeout return plain text, not an error. Subagents do not get the tool. With no client attached the result is `declined: no client could answer this question`. The tool has no HTML forms, images or password fields.
9. The edit review is opt-in and off by default, and it exists in dalgona only. The Edit review workstream gives its rules: a decision model judges each patch on many dimensions and judges each turn once; a flag reaches the working model only through two keys and only for a speaker; a failure never blocks an edit; recovery never judges.
10. The `ratchet` tool exists in dalgona only. Its gate is owned by the host: a frozen stratified split, content-hashed approvals for the inputs, the grader and the plan, completeness and held-out leak checks, a paired comparison case by case, keep, revert or rerun, a plateau rule and a round limit. Approvals go to the human through the ask tool's wire. A `ratchet` keyword notice carries the procedure.
11. The binary gains two or three new keyword notices, written in fresh words. No private skill text is copied.
12. When a sandbox is asked for and is not available, the user chooses once for a thread. `Accept`: every command asks, and session grants do not apply. `Dangerously accept`: commands run with no sandbox under the chosen approval mode. A cancelled question makes no choice: the command is declined, and the next command asks again. With no client attached, commands are declined unless the sandbox was turned off explicitly.
13. A rate limit that asks for a wait above 60 seconds: with a client attached, the product waits up to 300 seconds and shows `rate limited · retrying in <m>m <ss>s · esc stops`. Otherwise it stops with `rate limited for <s> s, over the <limit> s wait limit`.
14. `ultrathink` keeps its rule for one turn. The Anthropic encoder passes `xhigh` and `max` through. The status band shows the effort.
15. Backports: `NO_COLOR` and `DAL_NO_MOTION`; plain state words; one status row that drops whole items; one form for durations; compaction must shrink; a quota 429 and every 402 are terminal; replay of Anthropic `redacted_thinking`; safe MCP tool names; refusal of omission placeholders in edits; correct hashline status lines; a short terms list; a supersede rule and a "Rejected alternatives" section for decisions; device-code login for headless hosts; light or dark detection through the terminal's background colour.
16. Live debugging uses the project-local `tui` tool of oh-my-pi, installed under `.omp/tools` (ignored by git), and a scripted local chat-completions server. It needs no credentials.

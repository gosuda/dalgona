#### Decisions of the ask workstream

Each entry is a choice the product decisions do not settle, the rival, and the reason.

- D1. The model sees the tool as `ask`. Rival: `ask_user_question`. Reason: every thread tool is one plain word (`yield`, `task`, `todo`, `internal/tool/yield/yield.go:13`, `internal/tool/task/task.go:14`).
- D2. Keep the five-minute deadline from first publication under [Ask tool](../../../dal/spec/ask.md#host-path). A later subscriber or corrected answer never restarts it. Timed-out tool results identify the recommended fallback explicitly. Other consumers treat timeout as no answer. Keep `Waiting` plain and apply the existing reduced-motion rules.
- D3. On recovery, an `ask` with `tool.started` and no completion completes as `ok=false`, `recovered=interrupted`, with output `interrupted: the host restarted before the user answered`. It is never asked again. Rival: the class `read` row, "run the call again" (the `tool.started`, class `read` row under `## Rules` in `docs/spec/recovery.md`). Reason: recovery starts in the actor constructor before any client subscribes (`internal/agent/thread.go:132-136`). A rerun would always decline at daemon start and would race the window in `dal`, so the outcome would depend on timing.
- D4. The decline when the last window leaves lives in the actor: `actor.unsubscribe` answers every open question with "no client" once the subscriber set is empty. Rival: the server-side `declineIfAlone` pattern (`internal/rpc/serve_approval.go:137-143`). Reason: two windows that close at the same time each see 2 subscribers, neither declines, and the question hangs forever. The slow-subscriber close in `actor.publish` (`thread.go:489-498`) does not decline, because the server subscribes again at once (`internal/rpc/serve.go:291-309`).
- D5. A window cancels a question by answering with the result `{"answers": {}}`, the one cancel shape (cross-phase decision 9). Any other error response means "this window cannot answer". It declines with "no client" once every attached window has answered with an error. Until then the question stays open for the windows that have not answered. Rival: any error cancels. Reason: a headless `-p` client, an old client or an outside Codex client would otherwise cancel a question that a human in another window is reading.
- D6. Keep the vendored nested response: `{"answers":{"q1":{"answers":["value"]}}}`. Match option values by exact decoded scalar sequence. A display projection or normalized search key never identifies an option.
- D7. `serverRequest/resolved` carries `resolution`: `answered`, `cancelled`, `interrupted`, `timedOut`, or `declined`. Clients close a card on that notification, not on local submission.
- D8. Reject malformed encoding and NUL before offering questions or accepting answers. Keep accepted source text separate from safe display projections. Never repair malformed text with U+FFFD or use display cleanup as input validation.
- D9. A window that subscribes while a question is open receives that question again (replay in `actor.subscribe`). Rival: no replay, as with approvals. Reason: the user's task is "open the browser to answer the question my terminal just showed".
- D10. `ask` stays a direct tool in every tool mode and no Starlark cell, workflow or plugin can call it. Rival: fold it into `eval` like other tools. Reason: a durable cell that blocks on a person would hold the replay slot and get a nested call id (`<call_id>/<n>`). The window has no item for that id, and recovery would replay a human answer.
- D11. Both products get `ask`. Rival: `dalgona` only. Reason: it is a core tool (`internal/tool/**` is under the `core` depguard rule, `.golangci.yml:99-132`). It reaches the user only through `internal/rpc`, which both products already serve, and it imports no battery package. `docs/decisions/two-products.md` keeps `dal` as "the minimal agent and terminal interface", and asking the user is part of that interface. `dalgona` features such as the ratchet gate (product decision 10) reuses the same wire.
- D12. Answered, skipped, dismissed, and timed-out tool results are `ok=true`. No-client, interrupted, restarted, and failed outcomes are `ok=false`. Use the exact text from the current ask specification.
- D13. Question ids on the wire are `q1` to `q4` by position. The request id is `req-<16 lowercase chars>` from `newID("req-")` (`internal/agent/util.go:13-15`), the same as approvals.
- D14. Thread objects report `active` with `waitingOnUserInput` while a question is open, through a new `Status.Questions` count. Rival: only the live `thread/status/changed`. Reason: `thread/list` and the `/resume` picker would otherwise show `running` for a thread that waits on the user.
- D15. Clients mark the first option of each question `Recommended`, and the tool description tells the model so. Rival: the model appends "(Recommended)" to a label. Reason: one rule, and labels stay short.
- D16. Count Unicode scalars before display projection: header 30, question 500, label 80, description 300, preview 2000, and each answer 2000. Preview also retains its 40-line bound. Reject oversized values whole.
- D17. Keep core validation and client presentation within their existing package boundaries. Share the input contract and conformance fixtures without importing TUI or GUI code into core.
- D18. The question card's point (Design record, The point and the thread hue) is its submit action: the `s submit` hint in the terminal and the `Submit` button in the browser. Rival: the `Waiting` live tag, or the Enter key. Reason: submit is the one action that ends the decision in both windows, and the live tag is plain text while a card is open.
- D19. The state keeps its internal name `awaiting input`; the word shown to the user is `Waiting` (Design record, Motion and words). Rival: renaming the state to `waiting`. Reason: the state list that step 7 edits in `docs/spec/tui.md` is an internal name, and only the displayed word follows the design rules.
- D20. The browser card uses the ruled ledger card frame and the soft ledger controls (Design record, Components). Rival: a modal `<dialog>`. Reason: Design record, Components gives approval cards the ruled ledger, and the question card takes the approval card's place in the dock, inline and not modal (cross-phase decision 26; the web workstream, Step 21).
- D21. "No HTML forms" in product decision 8 limits what a question may ask. The ask card uses native fieldsets, radio buttons, checkboxes and one text input for "Other". Rival: using no form controls. Reason: native controls give keyboard and screen-reader behaviour for free.
- D22. Required model fields must pass the nonblank eligibility rule in [Ask tool](../../../dal/spec/ask.md#arguments). That derived check never trims accepted source or changes upper-limit counting.
- D23. Validate answer text before consuming the response waiter or claiming the host outcome. A typed client lifecycle retains its sender after the first response. Matching correction warnings permit a corrected answer under the same ID and original deadline.

Run `just verify` (`justfile:121`) before each commit. Commit messages carry no agent trailers.

#### Decisions of the Code symbols workstream

1. Modes of `search`, not new tools. Choice: `symbols`, `definition` and `syntax` are three modes of `search`, beside `find` and `grep`, in both products. Rival: three new tools, or one `code` tool with modes. Reason: a new tool repeats the walk, the ignore rules, the child process, the limits and the footers (`internal/tool/search/search.go:36`, `internal/tool/search/engine.go:39`). In eval-first mode the model sees `read`, `search`, `patch`, `apply_patch`, `exec` and `eval` (`internal/script/mode.go:13`), so the modes need no new name in that list. The modes share `path`, `glob`, `limit`, `literal` and `ignore_case` (the `args` struct, `internal/tool/search/json.go:15-23`).

2. One deep package, `internal/syntax`. Choice: bytes go in and rows come out. No tree, node, query or library type crosses the package boundary. The exported names of this workstream are the ones that the Schemas section lists. The code-rewrite workstream adds its own members later. Rival A: a wrapper that returns trees, which spreads the library import, the parse bounds and the parser setup across callers. Rival B: the library's aggregate registry with inferred queries (decisions 3 and 4). The table shows what each library surface becomes.

| Library surface | What reaches callers |
|---|---|
| `NewParser` (`parser.go:1640`) and `Parser` | Hidden. Used only inside `internal/syntax`. |
| `ParseStrict` (`parser_api.go:1829`) and `ParseWithTokenSourceFactoryStrict` (`parser_api.go:2053`) | Hidden. Called from `Parser.Symbols` and `Parser.Captures`. |
| `Tree`, `Node` and `Range` (`tree.go:14`) | Hidden. Callers see `Symbol`, `Capture` and `Report`. |
| `NewQuery` (`query.go:370`) and `Query.Execute` (`query.go:407`) | `Language.Compile` and `Parser.Captures` (Step 8). |
| `NewOutliner` (`outline.go:152`) and `OutlineTree` (`outline.go:239`) | `Parser.Symbols`. |
| `TokenSourceFactory` (`grammars/runtime/token_source_factory_registry.go:25`) | Hidden, through the adapter of Step 1. |
| Grammar packages `grammars/<name>` | Hidden behind `ForPath`, `ByName` and `Names`. |

3. Grammar packages, never the aggregate. Choice: import `github.com/odvcencio/gotreesitter/grammars/<name>` for each of the 23 names. The Go grammar package is named `golang` (`grammars/go/go.go:19` declares `Language`), so its import is aliased `golang`. Rival: the aggregate `grammars` package, which `gotreesitter@v0.57.0/docs/architecture.md:41` says holds all 206 blob-backed grammars. Four of them are copyleft: caddy, disassembly and jq under GPL-3.0, and nim under MPL-2.0 (`licenses/grammars.json`, `spdx` lines 257, 598, 1352 and 1704). The README leaves them out only when the build passes `-tags gotreesitter_no_copyleft` (`README.md:116-117`), so a build without the tag embeds them. Step 1 adds a depguard rule that refuses the aggregate and the four packages in every build. Standalone grammar packages need no build tags (`gotreesitter@v0.57.0/docs/architecture.md:42`). The owner fixed the 23 grammars, so `dal` and `dalgona` both link them. A throwaway program on 2026-11-12 measured these sizes on linux/amd64 with go1.27.4: no library 2.4 MB, the Go grammar 17.7 MB, 30 grammar packages 22.7 MB, the aggregate 36.9 MB. Steps 1 and 9 record the sizes of the binaries and of the 23 names.

4. Hand-written definition queries, one embedded file per language. Choice: `internal/syntax/queries/<name>.scm`, embedded with `go:embed`. Rival: the library's inferred tags queries (`grammars/tags_query_infer.go`). Those queries use the library's kinds, which this package does not choose, and they cover only some languages. `NewOutliner(lang, tagsQuery)` takes the query text (`outline.go:152`), so hand queries plug in.

5. A closed kind set and one mapping table. The eleven kinds are `function`, `method`, `class`, `interface`, `type`, `enum`, `constant`, `variable`, `module`, `macro` and `section`. The library passes an unlisted suffix through unchanged (`outline.go:22-32`). Its table also lists `constructor` (`outline.go:28`), and its refinement table maps `record_declaration` to `record` only when the capture is `type` or `class` (`outline.go:42-46`, and the applicability rule at `outline.go:49-52`). The package has one table, `kindOf`. The eleven kinds map to themselves, `constructor` maps to `method`, and `record` maps to `class`. Any other library kind returns `syntax: unknown kind KIND`. The hand queries write only closed kinds, so only the two refinement rows ever act. Rival: keep library kinds such as `struct` and `enum_member`. The `macro` kind is reserved, and no query in this workstream emits it.

6. Children. A child is listed only under a parent of kind `class`, `interface`, `type`, `module`, `enum` or `section`. Children of `function`, `method`, `constant` and `variable` are dropped with their subtrees. Reason: a definition inside a body is not a top-level name, and a list of locals buries the names. Impl blocks are not symbols, so a Rust method in an `impl` block is listed at depth 0. Test: `TestSymbolsLocalDefinitionsOmitted` (Step 1).

7. Name patterns. A pattern is an RE2 expression compiled with the flags of `grepRegexp` (`internal/tool/search/engine.go:258`), or plain text when `literal` is true. `ignore_case` adds `(?i)`. A pattern that is not literal is refused when `regexp/syntax` parses it into an empty-width operator: `OpBeginLine`, `OpEndLine`, `OpBeginText`, `OpEndText`, `OpWordBoundary` or `OpNoWordBoundary`, which come from `^`, `$`, `\A`, `\z`, `\b` and `\B`. Rival: allow anchors. Reason: an anchored pattern can skip a file that holds the name. For `^Run$`, the line `func Run() {}` does not match. The grep flags stay, and anchors are refused. The record of the later reviews states the same rule.

8. Narrowing by line, for `symbols` and `definition` only. With a non-empty pattern, `scanFile` (`engine.go:287`) runs first, and only files with a matching line become candidates. A name matches only on a line that contains it, so line narrowing keeps every file that holds a matching name when the pattern has no anchors. The bytes that `scanFile` read are reused for the parse. `scanFile` runs the whole regexp on each line of each searchable file (`engine.go:287-310`), so every file is read and only the parse is narrowed. In `syntax` mode the pattern is a tree-sitter query, so every file of the language is a candidate.

9. Bounds and one clock budget. The constants of the Schemas section are fixed by this workstream. A file over `parseMaxFileBytes` is not parsed. The file-count cap and the byte cap are checked in path order. `parseBudget` is a soft stop. The dispatcher reads the clock once per candidate, and once `parseBudget` has passed, every remaining candidate counts as stopped. `parseDeadline` is the hard stop. `runSearch` kills the child through the kill path, which Code search step 5 moves out of `Tool.Run` (`search.go:56-66` at commit `3c4b6f94`). The child has no deadline today, because `Tool.Run` passes the caller context to `collect` (`search.go:55`, `search.go:74`), and `runner.ProcessSpec` has no timeout field (`internal/runner/runner.go:21`). Rule: `parseDeadline` is at least `parseBudget` plus `parseTimeout` plus 10 seconds, which holds at 30 s against 22 s. Rival A: a kill at 10 s. A kill discards rows that a soft stop keeps. Rival B: a deadline without a budget. The budget returns the rows already parsed and a footer. The clock is passed in, so tests are repeatable. Issue #1600 reports that a timed parse can return an accepted tree after the deadline (https://github.com/odvcencio/gotreesitter/issues/1600). A parse that ends at or after `parseTimeout` therefore counts as stopped, and its tree is released.

The owner measured these values on one host under heavy load on 2026-11-12, one run each, with a 2 s parse timeout. They are observations, not benchmarks. A 939 KB Go file of one line parsed in 1.56 s with 232 MB peak resident memory. 540 KB of unbalanced Go tokens stopped at the timeout after 2.01 s with 102 MB. 30,000 nested brackets of Python (60 KB) parsed in 1.18 s with 83 MB. A 920 KB C file parsed in 2.05 s with 122 MB. 60 Go files of this repository (277 KB) parsed in 1.9 to 3.5 s. That run did not record the work limits in use, so Step 9 repeats these runs with the constants of this workstream.

Consequences. Three of the runs give 133 to 247 bytes of peak memory for each input byte (232 MB for 939 KB, 102 MB for 540 KB, 122 MB for 920 KB). The Python run gives 83 MB for 60 KB, which is about 1,380 bytes for each input byte. The owner's statement that memory was at most about 250 bytes for each input byte does not hold for that run, and this workstream corrects it. At 1,380 bytes for each byte, a 256 KiB file needs about 360 MB, which is above the 256 MiB per-parse budget of decision 10, so the budget ends that parse as a stop and it gives no rows. The timeout ends a bad parse at about 2 s. A valid parse that takes 2.05 s, like the 920 KB C file, is counted as stopped by the rule above, so the symbols mode gives it no rows. The 256 KiB file cap keeps files of that size out of the symbols mode.

10. Memory and work limits on every parser. Choice: `SetMemoryBudgetBytes(parseMemoryBudgetBytes)` with 256 MiB (`parser_api.go:1271`), and `SetParseWorkLimits` with `IterationLimit` 200,000, `StackDepthLimit` 8,192 and `NodeLimit` 1,000,000 (`parser_api.go:1123-1129`, setter at `:1299`). The library default budget is the larger of 512 MiB and 512 bytes for each input byte (`gotreesitter@v0.57.0/docs/api-guide.md:51-52`), so a 16 MiB file could reach 8 GiB. The process-heap ceiling is the larger of 2 GiB and twice the budget (`parser_api.go:1264-1266`), so one call with 8 workers can hold about 2 GiB of live parse memory (8 times 256 MiB). A parse stopped by the budget returns a partial tree with a nil error on the plain methods, and it returns `ParseStoppedEarlyError` on the strict methods (`parser_api.go:1268-1270`). The work limits can change tree selection (`gotreesitter@v0.57.0/docs/api-guide.md:48`). The fixtures check the rows, and Step 9 checks the peak memory.

11. Strict parse on both lexer routes. Choice: `Parser.parse` calls `ParseWithTokenSourceFactoryStrict(src, f)` (`parser_api.go:2053`) when `grammarruntime.TokenSourceFactory(name)` returns a factory (`grammars/runtime/token_source_factory_registry.go:25`), and it calls `ParseStrict(src)` (`parser_api.go:1829`) otherwise. The runtime factory has the type `func(src []byte, lang *gotreesitter.Language) gotreesitter.TokenSource`. The strict route takes `gotreesitter.TokenSourceFactory`, which is `func(source []byte) (TokenSource, error)` (`parser_api.go:67`). Step 1 writes the adapter `tokenSourceFactory`, which binds `lang` and returns a nil error. The factories for `c`, `cpp` and `java` are registered at `grammars/runtime/token_source_factory_builtin.go:15-16` and `:57`. `ErrParseStoppedEarly` is at `parser_api.go:2775`, and `ParseStoppedEarlyError.Is` matches it (`parser_api.go:37-38`). Issue #1558 reports that the plain route on a 20-byte C++ input never returns without a timeout, and that the factory route stops with `no_stacks_alive` in about 2 ms (https://github.com/odvcencio/gotreesitter/issues/1558). C++ takes the factory route here, so the strict call turns that stop into no rows.

12. Release and caps. Each tree is released with `tree.Release()` after its rows are copied (`tree.go:4149`). The method is nil-safe (`tree.go:4150`). A syntax query returns at most `limit` captures. The rest are counted in `[Truncated: N more captures]`.

13. Concurrency. A `Parser` is not safe for concurrent use (`parser.go:22-23`). Each worker keeps one `Parser` per language, created on first use. The worker count is `parseWorkers`, a package constant of value 8 (Code symbols step 6), which step 9 changes through `parseWorkerCount`. A compiled `Query` is safe for concurrent `Execute` after construction (`query.go:13-15`). An `Outliner` is safe for concurrent `OutlineTree` (`outline.go:61-63`). Each language caches its outliner with `sync.OnceValues`. The package calls no package-level setter, which avoids the races in issue #1532 (https://github.com/odvcencio/gotreesitter/issues/1532).

14. Determinism. Candidates are walked in display-path order, because `walkScope` sorts entries by display path (`engine.go:121`). One dispatcher hands candidates to workers in that order, and results are stored by candidate index. Output does not depend on worker timing, except when the clock passes `parseBudget`. A scripted clock makes that repeatable in tests.

15. Footers name every omission, and they follow the rows. The rows of a call come first, in path order and then line order. The footers follow in this order: the `[Parse: stopped, no rows: PATH]` and `[Parse: syntax errors, rows kept: PATH]` lines, in path order; then `[Not parsed: ...]`; then `[Syntax only: ...]`; then `[Stopped: ...]`; and `[Truncated: ...]` last. Rival: silent omission. Parse problems and bounds must not look like absent definitions.

16. Parse problems keep or drop rows. A tree with syntax errors keeps its rows and gets `[Parse: syntax errors, rows kept: PATH]`. A stopped parse gives no rows and gets `[Parse: stopped, no rows: PATH]`. Rival: drop every file with an error. A file with one bad construct still has useful rows, and a stopped parse has no trustworthy tree.

17. Snapshot tags. Symbol rows and syntax rows carry no snapshot tags. `docs/spec/edit-styles.md:9` places symbol locators and symbol search outside the edit contract. Definition output differs on purpose. It returns one file capture with the printed line ranges, so `makeResult` (`search.go:124`) adds the file's `[PATH#tag]` line, and a body row can feed a `patch` call. Rival: no capture for definition, which would leave a body row that `patch` cannot cite.

18. Row forms. A header row is `PATH:START-END: KIND TEXT`, with two spaces before the path for each level of depth. The same indent rule applies to symbol rows and to definition headers. A body row is `PATH:LINE: TEXT`, the form that `appendFileRows` writes (`engine.go:375`, format `%s:%d%c %s` with the colon marker). A syntax row is `PATH:LINE: CAPTURE: TEXT`, with no at sign. A header's text is the first source line of the definition, with leading spaces and tabs removed. Other text is cut by `cropMatch` (`engine.go:391`), which keeps 500 runes and appends `...`.

19. One language table. A single table, `registry`, in `internal/syntax/language.go`, holds for each language its name, extensions, grammar function and embedded query. A language with an empty query is syntax only. Adding a language touches that row, one query file and one fixture. Rival: three files for grammar, query and extension map. Those would drift apart.

20. Language selection and the shared extension. `symbols` and `definition` skip syntax-only files, which have no definition query. When such files are in scope, the reply adds `[Syntax only: N files. Use mode syntax with lang.]`. Files whose extension is outside the table are skipped without a footer. The grep path skips binary text the same way (`engine.go:313-315`). `syntax` includes syntax-only languages. The shared extension `.h` belongs to `c`. The extension table says so, the specification text says so, and `lang` in `syntax` mode selects files by this table, so `lang` `cpp` never selects a `.h` file.

21. Parser setup in one place. `Language.NewParser` calls `newParser(lang, parseTimeout)`, which sets the timeout, the memory budget and the work limits once, for every parser the package creates. `Parser.Symbols` and `Parser.Captures` read `ctx.Err()` before they parse.

22. Fixtures use hand-written expected rows. Each fixture's expected rows are written before its query and checked against the forms in this workstream. A saved output proves only that the parser has not changed. A row that its fixture does not confirm is deleted with its fixture lines, and the kind table then names the gap. Every row that depends on a node name taken from upstream grammar files, rather than from the library blobs, follows this rule.

23. Error texts are final per step. The Schemas section lists the final texts. Steps 6 and 7 state the interim texts that hold until Step 8. Each error names the next call that the caller can make, and the unknown `lang` error lists the 23 names.

24. Specification and notices. The section `## Symbols and syntax` in `docs/spec/search.md` lands in Step 6, after `## Index`. Code search step 3 puts `## Index` directly after `## Scanning`, which is line 3 of that file at commit `3c4b6f94`. It grows in Steps 7 and 8. `THIRD_PARTY_NOTICES.md` is created in Step 1 under `# Third-party notices`, as this plan rule asks. Step 1 adds the sections for `gotreesitter` and for the `go` grammar. Each later step adds the sections for its own grammars. Each section holds the copyright lines and the MIT permission text of the grammar's LICENSE file at the URL in the Schemas table. Source: `licenses/grammars.json` (the owner checked the MIT licences on 2026-11-12) and the library LICENSE file (`LICENSE:1-3`).

25. The sibling rewrite tool. `Capture` carries `Match int`, the index of the match in match order. Captures of one match are adjacent, and `Parser.Captures` returns them in that order. This workstream adds no rewrite code.

26. Cells and eval-first are unchanged. The owner's defaults stand: `tool_mode` is `eval-first` in both products, and a cell may call every tool except `eval`. `search` is visible in eval-first (`internal/script/mode.go:13`), so the modes need no cell change.

27. Benchmarks report numbers and move no constant. Step 9 writes the numbers to `docs/decisions/syntax-package.md`. A later change to a constant needs a new entry in that file.

28. Two benchmarks are left out: parser reuse, and outline against tree walk. Decisions 13 and 5 already fix those choices, so the comparisons would not change a choice.

29. Kind names are unexported. The eleven kind names are unexported constants in `internal/syntax`, because the search tool is the only caller of the names, and it owns their list (below). The search tool keeps its own list of the eleven names (`symbolKinds` in `parse.go`), and `TestKindListMatchesSchema` in Step 6 ties that list to the schema enum. Rival: an exported `Kinds()` function. Rejected, because the search tool is the only caller, and `symbolKinds` already holds the eleven names, which `TestKindListMatchesSchema` ties to the schema. An exported copy would add a second list with no new caller.

30. Extension table follows the library lock. Bash takes `.sh` only, and markdown takes `.md` only, as `grammars/languages.lock` lists them (`:3` for bash, `:43` for markdown). The extensions `.bash` and `.markdown` are not in the table. Rival: add them. Rejected, because the table should match the library's own extension data.

31. Method and function kinds. Python methods, C++ methods, Kotlin and Swift member functions, Rust functions in `impl` and `trait` bodies, and Ruby `def` in a class or module body are `method`. Top-level functions are `function`, including Ruby top-level `def` and `def obj.m`. Rival: all functions as `function`. Rejected, because a filter on `method` must work across languages.

32. C lists definitions only, not prototypes. Function definitions are listed up to two pointer levels, as in `char *label(void) {...}`. Rival: prototypes too. Rejected, because a prototype has no body for `definition` to read, and every header function would appear twice in a project.

33. Go package-level `const` and `var` list only the first name of each spec. Rival: one row per name. The library refuses that shape, because a node with two names is an `OmittedNameConflict` (`grammars/tags_query_infer.go:129-132`, which states the rule). The Go fixture uses single-name specs.

34. Python decorated definitions span their decorators. The start line of a decorated function is its first decorator line. Rival: the `def` or `class` line. Rejected, because `definition` prints from the start line, and a body without its decorators would be misleading.

35. Kotlin classes need a body to be listed. The grammar makes `class_body` optional, so body-less classes are not listed, and the Kotlin kind table says so. Enum classes carry `enum_class_body`, so the class row does not match them. Rival: a predicate that excludes the enum modifier. Not used, because the support for that predicate in this query engine was not checked.

36. Markdown headings are `section` nodes. A heading's span is its `section` node, so `definition` reads the heading and its body, including its subsections. Rival: the heading line only, which gives `definition` nothing to read. A section ends where a heading of the same or higher level starts. The Step 4 fixture checks that rule.

37. Not listed. TypeScript dotted namespaces (`namespace A.B {}`), Kotlin and Swift properties, Java enum constants, and Rust macros are not listed. Rust `macro_definition` is not listed because `macro` is reserved and no query emits it.

38. Records and annotation types. Java `record_declaration` and C# `record_declaration` use `@definition.class`, which the library refines to `record`, and the package maps `record` to `class` (decision 5). Java `annotation_type_declaration` maps to `interface`.

39. Lua. Dot functions and colon functions are `method`. `local function` is `function`.

40. Ruby names. `class A::B` is listed under its full scope name. A setter `def name=(v)` is listed as `name=`.

41. Notices are written by hand, one section per module, not generated. Rival: a list generated from each module's LICENSE file. Rejected, because this plan rule for notices names a fixed list, and this list is the one that the Notices table of the Schemas section gives.

42. Dependency rows. `github.com/odvcencio/gotreesitter` gets one row in `docs/decisions/dependencies.md`. `golang.org/x/sync` (`go.mod:29`, direct, v0.24.0 now and v0.25.0 after Version pins step 3) and `gopkg.in/yaml.v3` (`go.mod:309`, indirect, v3.0.1) get no new row. Both are already in `go.mod`, and no library package of gotreesitter imports them, because the grep excluded `cmd` and test files. Both already have rows in the Version pins table. Rival: add rows for both now. Rejected, because a row is for a new dependency, as the repository rule says.

43. Modes of the schema. Each step adds its own mode to the `mode` enum, and the final enum is in the Schemas section.

44. Context in the child. `symbolsMode` takes `ctx context.Context` first. `execute` passes `context.Background()`, because the child has no deadline and the parent kill is the hard stop. Rival: change `execute` to take a context. Rejected, because that changes every existing caller and test of `execute`.

45. Clock. `symbolsMode` receives `now func() time.Time` and calls it once per candidate and nowhere else. Tests pass a scripted clock.

46. Context wrapping by mode. `Tool.Run` wraps the context with `parseDeadline` for each mode from its own step: `symbols` in Step 6, `definition` in Step 7, and `syntax` in Step 8.

47. Empty replies and footers. When there are no rows, the empty reply is the first line, and the footers follow it.

48. Changelog. The repository has no changelog file at commit `3c4b6f94`, because neither `docs/changelog` nor `CHANGELOG.md` exists. No step adds a changelog line.

49. Hostile-input tests. The three hostile tests of Step 3 wait for the call with a `select` on `time.After(10 * time.Second)`, and never call `time.Sleep`. The library's timeout stops the parse, and the test only bounds its wait.

50. Search tool error texts for the mode list. Step 6 holds `search: mode must be find, grep, or symbols`, Step 7 holds `search: mode must be find, grep, symbols, or definition`, and Step 8 holds the final text of the Schemas section.

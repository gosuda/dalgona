#### Outcome of the code-search workstream

The `grep` mode of the `search` tool reads only the files that can match, and its output stays byte for byte equal to today's output. A trigram index from `github.com/google/codesearch` v1.2.0 names the candidate files. The index lives under the product home, in `<home>/search/<hash16>/`, where `<home>` is the `Home` field of `tool.Env`. A hidden child builds each index into a new generation directory that only that child can write. The parent publishes a generation only after the build exits with status 0. A search skips a file only when a fresh record covers it and its trigram query does not name it. Each call still walks the scope and stats every file. The index applies only where the sandbox enforces its writable roots, on a local runner, and on platforms with change times. Elsewhere the engine reads every file, as it does today. A grep call that reads at least `indexRebuildBytes` of counted uncovered bytes starts one background build after the call returns. The counter adds only the bytes of files that the call reads: a file that the engine never reads (one over 16 MiB, or one that is not regular) adds nothing, so it cannot trigger a build. The `find` mode does not change, and this workstream does not change the model-visible schema of `search`.

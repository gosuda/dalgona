#### Terminal step 14. Commit once, row grammar, tool cards and file diffs

- `rows.go`: `commit` is the Structure rule. Add `type row struct{ mark, label, subject, state, meta, duration string; body []string }` and `func (m *model) renderRow(r row) []string`. The result is the row line first, then the body lines. The row draws the Measured ledger of the Design record, Terminal rows: an optional two-cell `mark` (used by the user and shell rows), then the state column (10 cells), the label column (7 cells, cut with `fit`), the subject (the rest of the width, cut with `fit` first), the meta column (9 cells), and the duration column (8 cells, right-aligned). The row line is at most `terminalWidth(m.screen.width)` cells. Column widths are fixed, so rows line up at one width. Body lines start under the subject column and wrap with `wrap` at the width that is left after that column. A blank line separates committed rows, and body lines follow their row directly. Word map: `completed` gives `Done` in `dim`, `failed` gives `Failed` in bold `failed-text` (Design record, The point and the thread hue: never a fill), `declined` gives `Declined` in `dim`, `inProgress` gives `Working` in `text`.
- Print path: a row prints only through `commit(key, m.renderRow(r))`. `commit` queues the lines, and `drain` (Structure) wraps them and converts colours through `m.screen.emit`. `tea.Println` then writes that text verbatim above the frame (`bubbletea/v2@v2.1.1/cursed_renderer.go:771-830`). `emit` is the only colour conversion a row gets. Verification: `TestNoColorFrameHasNoColourSequences` (Step 9) covers the colour rule. A pty run under `NO_COLOR=1` prints one row and asserts that the captured bytes hold no such SGR.
- Per item, replacing `renderSettledItem` (`render.go:125-146`), which now returns the lines of the row:
  - userMessage: mark `›` in the text colour of the thread hue, as the prompt mark is (Design record, The point and the thread hue). The body is the text with keyword marks.
  - agentMessage: no row. Its text prints as final blocks (Step 17), and its last tail prints at completion.
  - reasoning: label `Thinking`, the text as body (verbosity in Step 16).
  - commandExecution: mark `$`, subject is the first command line, meta `exit N`, duration from `liveItem`, body is the output.
  - fileChange: one row per change. The label is `Created` for kind `add`, `Deleted` for `delete`, `Edited` for `update` (`internal/rpc/serve_track.go:233-239`: `add` when there is no pre-image, `delete` when there is no post-image). Subject is the path, meta `+A −D` (the change's `additions` and `deletions`, protocol Schemas), body the diff lines with signs kept and painted `roleAddedText` (added), `roleFailedText` (deleted) or `roleDim` (meta). More than one file adds the header `Changed N files`. A change with `diffOmitted` true has meta `diff omitted` and the body `diff omitted, larger than 1 MiB`, and shows no counts (cross-phase decision 42).
  - mcpToolCall: label `Called`, subject `server/tool`.
  - dynamicToolCall: the label is the tool name with its first letter upper case. The subject is the first present of the arguments `path`, `pattern`, `url`, `prompt`, `code` (first line), decoded with `encoding/json/v2` (cold data). A `task` call takes the label `Subagent` (Step 18), and a successful `todo` call writes no tool row (Step 18).
  - contextCompaction: label `Compacted context`.
  - the verdict rows of `dalgona/tool/judged` and `dalgona/turn/judged` belong to the edit-review workstream, Step 7. That step prints them through `commit` with keys `review:<threadId>:<itemId>` and `review:<threadId>:<turnId>`. This step adds no row for them.
- Nested calls. A call that an `eval` cell makes is an ordinary item with id `<run>/<n>`. `internal/scripthost/effects.go:61` defines `callID(run, n)` as `run + "/" + strconv.Itoa(n)`. `CallTool` builds the nested `event.ToolCall` with it and calls `RunNestedCall` (`effects.go:342-343`). `<run>` is the eval call id, because `eval` starts its run with `RunStart{ID: call.ID}` (`internal/script/eval.go:85`). `Thread.RunNestedCall` (`internal/agent/extension.go:87`) and `runNestedCall` (`extension.go:103`) admit the call, which appends `ToolStarted` with that id (`internal/agent/tools.go:252`, `:324-326`), and the completion that `execute` returns is appended with the same id. The tracker turns each `tool.started` and `tool.completed` into `item/started` and `item/completed` with no filter on the id (`internal/rpc/serve_track.go:256-266`, `:268-289`). The kind comes from the class (`toolItem`, `serve_track.go:215-216`; `toolKind`, `internal/rpc/serve_items.go:147-159`): `read`, `agent` and `script` give `dynamicToolCall`, `edit` gives `fileChange`, `exec` gives `commandExecution`, and `remote` gives `mcpToolCall`. The classes are `todo` read (`internal/tool/todo/todo.go:32`), `task` agent (`internal/tool/task/task.go:42`), `web_fetch` read (`internal/tool/webfetch/fetch.go:60`) and `eval` script (`internal/script/eval.go:78`).
- The client reads the id as text. `liveItem` matches `item.ID == id` (`internal/tui/model.go:454-458`), and the keys of this workstream hold the id as text. No code in `internal/tui` splits an item id, so the slash in `<run>/<n>` is inert. `executeSlash` cuts only the typed line (`commands.go:196`).
- What the terminal shows for an eval and its nested calls. The eval item prints one row when it completes: its row of this step, or the one-line form of Step 16 at medium. Each nested call completes before the eval, so its row prints first, in time order, and the rows do not nest. A successful `todo` prints no tool row, and it changes the plan row and plan field (Step 18). A `task` prints the `Subagent` row (Step 18). A `read`, `search` or `web_fetch` prints its class row (`Read`, `Search`, `Web_fetch`), with the subject from its arguments. A `patch` prints an `Edited` row, and an `exec` prints a `$` row. A failed nested call prints its row with state `Failed`.
